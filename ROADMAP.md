# Roadmap

What is being built, in what order, and why that order. Decisions here are made,
not open questions. If something needs revisiting, change it here first.

## Locked decisions

| Decision | Choice | Why |
| --- | --- | --- |
| Desktop app framework | Tauri v2 | ~5MB installers against Electron's ~100MB. A configurator for a 12KB script should not be heavier than the thing it configures. |
| App shape | Window first, tray second | Tray is a superset of the window, so nothing is thrown away. Shipping the window first means something usable exists sooner. |
| App and scripts | App bundles the scripts and installs them itself | Someone who wants the app never touches a terminal. The `curl` and `irm` route keeps working unchanged. Two front doors, one engine. |
| Code signing | None, ever | Nothing in this project costs money. Unsigned means a Gatekeeper prompt on macOS and a SmartScreen warning on Windows, both documented. Tauri's updater signs with its own free keypair and is unaffected. |
| Repo layout | One repo, app under `app/` | Shared CI and one issue tracker. Tags disambiguate: `v1.2.0` for the scripts, `app-v0.1.0` for the app. |
| Release artifacts | Per platform, attached to one release | `.msi` for Windows, `.AppImage` and `.deb` for Linux, `.dmg` for macOS, plus the two installer scripts. |
| Scripts stay standalone | Always | The hooks own the alerting. The app only writes config and reads state. Uninstalling the app must leave alerts working. This is the property that protects existing users, and it is not negotiable for a feature. |

## The ordering rule

Anything the app's UI depends on ships **before** the app. Building the app
against a config that is about to change means building the UI twice. Concretely:
the app has a sound picker, so the set of sounds has to be known and consistent
first, or the picker just lists whatever each machine happens to have and cannot
preview reliably.

## Phase 0 — Single source of truth (done)

Notifiers extracted to `notifier/`, installers generated from `templates/` by
`build/generate.py`, CI fails on drift. The app can now ship the same notifier
the scripts use rather than a second copy.

## Phase 1 — v1.2.0, scripts only

Everything the app will need to configure.

- [x] Per-event options: `_ENABLED`, `_VOLUME`, `_PATTERN`, `_SOUND`
- [x] Rhythm patterns (`3x140`)
- [x] Quiet hours
- [x] `CLAUDE_NOTIFY_DRYRUN=1`, which the app also needs for previewing
- [ ] **Bundled sounds** — a known set, shipped with the project
- [ ] **Sound packs** — a pack is a folder, so people can make their own
- [ ] Docs and a v1.2.0 release

**Bundled sounds is a decision, not a question.** It ships, and it ships before
the app. It removes the `sound=none` failure mode on minimal Linux installs, it
makes `PROJECT_PITCH` meaningful rather than dependent on whatever the OS
provides, and it is what makes an app sound picker possible at all.

The cost is that the single-file installers must carry the audio as base64,
adding roughly 60-90KB each. Mitigation: the blob goes at the very end behind a
clear marker, so the readable part of the script stays readable, and the header
comment says where it ends. The sounds are generated by a committed script, so
they are reproducible and carry no licensing question.

**Exit criteria:** every alert kind resolves to a bundled sound on a machine with
no system sounds at all, CI asserts it, and the scripts are feature-complete.

## Phase 2 — app v0.1, the window

- Per-event rows: toggle, sound dropdown, **play button**, volume, pattern
- Suppression settings in plain language
- Install and uninstall the hooks from the app, using the bundled scripts
- Detect and adopt an existing script install rather than fighting it
- Recent alert log: what fired, what was suppressed and why

**Exit criteria:** a fresh machine with no terminal use gets working alerts, and
uninstalling the app leaves them working.

## Phase 3 — app v0.2, the tray

- Quick mute and "quiet for 1 hour"
- Quiet hours UI over the Phase 1 config
- Live status and a running alert feed
- **Escalation** — re-alert if a blocked prompt goes unanswered. The only
  feature that genuinely needs a resident process, since a hook exits at once.
- Launch at login, opt in

## Deliberately not doing

| Idea | Why not |
| --- | --- |
| Electron | Size, for a tool whose selling point is being small. |
| Slack or Discord integration | Scope creep. A webhook is one `curl` if anyone wants it. |
| Usage analytics | Kills trust for something watching your dev session. |
| Custom sound recording in-app | People have files. A path field is enough. |
| Homebrew tap, winget manifest | Packaging overhead before anyone has asked. |
| Rewriting the notifier in Rust | It runs on every turn and must stay dependency-free. Shell and PowerShell are already installed everywhere. |

## Open, and deliberately deferred

- **Remote push** to a phone via ntfy.sh. Genuinely useful for long runs, free,
  but it is a Phase 3 concern at the earliest.
- **More hook events** — `PreCompact` is the interesting one. Cheap to add once
  the config shape has settled.
